# PRD: приложение подготовки Word-анкеты к сравнению со скриптом

## 1. Контекст и проблема

В рабочей папке лежит 21 проект. Один проект соответствует одной папке с числовым ID. Почти в каждом проекте есть:

- Word-анкета `.docx`;
- скрипт `.txt`, который уже содержит программную структуру анкеты;
- паспорт `.xlsx`, из которого берутся квоты.

Исключение: в проекте `331778` паспорт `.xlsx` не найден.

Сейчас анкета в Word не готова к автоматическому сравнению со скриптом: вопросы, инструкции, варианты ответов, таблицы кодировок и служебные блоки записаны в разных форматах. Нужно приложение, которое загрузит Word-анкету, автоматически разделит ее на вопросы и даст пользователю проверить/исправить структуру перед сравнением со скриптом.

## 2. Цель продукта

Сделать инструмент подготовки анкеты, который превращает `.docx` в нормализованную структуру:

- начало и конец каждого вопроса;
- код вопроса;
- формулировка вопроса `title`;
- тип вопроса;
- варианты ответов `options`;
- строки/колонки для матриц и гридов;
- инструкции, условия показа, скрины, квоты и служебные примечания как отдельные поля.

Результат должен быть пригоден для дальнейшего автоматического сравнения с `.txt`-скриптом.

## 3. Пользователи

Основной пользователь: специалист, который проверяет соответствие анкеты и скрипта перед запуском/передачей в программирование.

Типовые задачи пользователя:

- загрузить Word-анкету;
- увидеть автоматически найденные вопросы;
- проверить, где начинается и заканчивается каждый вопрос;
- отделить формулировку от вариантов ответов;
- исправить ошибки автопарсинга;
- выгрузить структурированный файл для сравнения со скриптом.

## 4. Наблюдения по текущим проектам

Форматы начала вопросов в Word различаются:

- `S1.`, `S2.`, `S2a.`;
- `QS1.`, `QS2age.`;
- `Q1.`, `QDataM.`, `QEX.`;
- `D1.`, `D5.`;
- брендовые коды вроде `BEER1.`;
- служебные вопросы вроде `Strata.`;
- иногда вопрос начинается в обычном абзаце, а варианты идут в таблице;
- иногда и сам вопрос, и варианты записаны внутри таблицы.

В скриптах встречаются типы:

- `Single`;
- `Multi`;
- `Free`;
- `Matrix`;
- `Grid`;
- `Rank`;
- `Scale`;
- `Info`;
- `Group`.

Скрипт обычно имеет структуру:

```txt
QS1. Укажите ваш пол
type: Single
columns: 2
options:
1. Женский
2. Мужской
```

В начале многих скриптов идут блоки квот:

```txt
start quotafilter
code: ...
name: ...
condition: ...
quota: ...
min_quota: ...
end quotafilter
```

Эти блоки не являются вопросами, но важны для дальнейшего сравнения с паспортом.

## 5. Область MVP

MVP должен решать только подготовку Word-анкеты. Сравнение со скриптом может быть следующим этапом, но модель данных должна сразу быть совместимой со скриптом.

В MVP входит:

1. HTML-страница приложения, которую пользователь открывает в браузере.
2. Загрузка `.docx` через интерфейс страницы.
3. Извлечение структуры Word через OOXML, а не только через плоский текст.
4. Автоматическое определение границ вопросов.
5. Автоматическое выделение `code`, `title`, `type`, `options`, `rows`, `columns`, `instructions`.
6. Визуальный экран ручной проверки и исправления.
7. Экспорт результата в новый `.docx` с видимой и машинно читаемой разметкой.
8. Сохранение правок пользователя.

В MVP не входит:

- полное автоматическое сравнение со скриптом;
- изменение исходного Word-файла;
- полноценный редактор `.txt`-скрипта;
- генерация финального скрипта.

Дополнительное ограничение MVP: приложение должно работать как один локальный файл `index.html`. Парсинг `.docx`, ручная разметка и формирование выходных файлов выполняются полностью в браузере, без Python-backend, локального сервера и загрузки документов во внешние сервисы.

## 6. Входные данные

### Обязательные

- `.docx` анкета.

### Опциональные на этапе MVP

- `.txt` скрипт для предпросмотра будущего сравнения;
- `.xlsx` паспорт для отображения доступных листов и квотных таблиц.

## 7. Выходные данные

Основной результат работы приложения: новый Word-файл с разметкой анкеты.

Исходный `.docx` не изменяется. Приложение создает копию, например:

- `questionnaire_prepared_for_script_compare.docx`;
- или `<исходное_имя>__prepared.docx`.

В размеченном Word должны быть явно видны:

- начало каждого вопроса;
- конец каждого вопроса;
- код вопроса;
- блок `title`;
- блок `options`;
- строки/колонки для матриц и гридов;
- инструкции, скрины, переходы и служебные комментарии.

Рекомендуемый формат разметки в Word:

- перед каждым вопросом вставляется служебная строка с нормализованным кодом: `[QUESTION_START code=QS1 original=S1 type=Single]`;
- после каждого вопроса вставляется служебная строка с нормализованным кодом: `[QUESTION_END code=QS1]`;
- формулировка помечается строкой/комментарием: `[TITLE_START] ... [TITLE_END]`;
- варианты ответов помечаются строками/комментарием: `[OPTIONS_START] ... [OPTIONS_END]`;
- для таблиц допускается пометка всей таблицы как `OPTIONS`, `ROWS`, `COLUMNS` или `MATRIX`;
- спорные места выделяются цветом и/или комментарием Word `needs_review`.

Требование к разметке: она должна быть понятна человеку в Word и одновременно машинно читаема для следующего этапа сравнения со скриптом.

Дополнительные экспорты:

- `prepared_questionnaire.md` - человекочитаемая версия;
- `prepared_questionnaire.html` - отчет с подсветкой сомнительных мест.

## 8. Модель данных вопроса

Минимальные поля:

- `code` - исходный код вопроса из анкеты: `S1`, `QS1`, `QDataM`, `D1`, `BEER1`;
- `normalized_code` - исправленный код для выходного Word и будущего сравнения со скриптом;
- `title` - формулировка вопроса без вариантов ответа;
- `type` - тип вопроса в терминах скрипта;
- `options` - варианты ответов;
- `rows` - строки матрицы/грида;
- `columns` - колонки матрицы/грида;
- `instructions` - инструкции интервьюеру/программисту;
- `conditions` - переходы, скрины, условия показа;
- `quotas_refs` - ссылки на квотные переменные, если они явно видны;
- `source_blocks` - исходные блоки Word;
- `confidence` - уверенность автопарсинга;
- `needs_review` - требуется ли ручная проверка.

Для варианта ответа:

- `code`;
- `text`;
- `is_exclusive`;
- `is_open`;
- `is_screenout`;
- `is_other`;
- `comments`;
- `source_block`.

## 8.1. Нормализация лейблов вопросов

В выходном размеченном Word все лейблы вопросов должны начинаться с `Q`.

Парсер должен:

1. Найти исходный лейбл вопроса в анкете.
2. Сохранить исходный лейбл в поле `code`.
3. Рассчитать исправленный лейбл в поле `normalized_code`.
4. В обновленный Word добавлять именно `normalized_code`.
5. Если исходный лейбл был изменен, добавить видимую пометку и/или комментарий: `original=S1 normalized=QS1`.

Правила нормализации:

- если код уже начинается с `Q`, префикс не добавляется;
- если код не начинается с `Q`, добавить `Q` в начало;
- точки внутри кода заменить на маленькую букву `p`;
- нижние подчеркивания внутри кода заменить на маленькую букву `p`;
- регистр исходных букв после добавления `Q` сохраняется;
- техническая вставка `p` всегда должна быть маленькой.

Примеры:

- `S1` -> `QS1`;
- `D1` -> `QD1`;
- `D4.1` -> `QD4p1`;
- `S1.1` -> `QS1p1`;
- `Q1_2` -> `Q1p2`;
- `QS2age` -> `QS2age`;
- `QDataM` -> `QDataM`.

Если после нормализации два вопроса получают одинаковый `normalized_code`, оба вопроса должны получить статус `needs_review`.

## 9. Требования к парсеру Word

Парсер должен читать `.docx` как OOXML и сохранять порядок блоков:

- абзацы;
- таблицы;
- строки и ячейки таблиц;
- списки;
- жирный/курсив/подчеркивание;
- цвет текста и выделение;
- комментарии Word, если есть;
- переносы строк внутри ячеек.

Парсер должен уметь находить начало вопроса по паттернам:

- `S1.`, `S1.1.`, `S2a.`;
- `QS1.`, `QS2age.`;
- `Q1.`, `QDataM.`, `QEX.`;
- `D1.`, `D5age.`;
- буквенно-цифровые коды: `BEER1.`, `B1.`, `Strata.`;
- коды без точки, если они визуально отделены стилем или строкой.

Конец вопроса определяется как блок перед следующим уверенно найденным началом вопроса. Если между вопросами есть заголовок секции, он должен сохраняться как `section` или `instruction`, а не теряться.

## 10. Выделение title и options

`title`:

- начинается после кода вопроса;
- может занимать несколько абзацев;
- заканчивается перед списком вариантов, таблицей кодировок, строками `1.`, `1)`, `1 |`, `1. |`;
- не должен включать технические инструкции типа `ОДИН ОТВЕТ`, `МНОЖЕСТВЕННЫЙ ВЫБОР`, `СКРИН`, если они вынесены отдельной строкой.

`options`:

- распознаются из абзацев и таблиц;
- поддерживают форматы `1. Текст`, `1) Текст`, `1 | Текст`, таблицы с колонками `код / текст / инструкция`;
- сохраняют служебные пометки: `СКРИН`, `ЗАВЕРШИТЬ ОПРОС`, `Другое`, `Ничего из перечисленного`, `Затрудняюсь ответить`;
- должны сохранять исходный порядок.

## 11. Определение типа вопроса

Автоопределение типа должно работать по текстовым маркерам:

- `один ответ`, `одиночный выбор` -> `Single`;
- `несколько ответов`, `множественный выбор` -> `Multi`;
- `открытый вопрос`, `впишите`, `укажите текстом` -> `Free`;
- таблица с наборами строк и колонок -> `Matrix` или `Grid`;
- `ранжируйте`, `расположите` -> `Rank`;
- только информационный экран без вариантов -> `Info`.

Если тип не определен надежно, ставить `type: Unknown`, `needs_review: true`.

## 12. Интерфейс приложения

Основной экран должен быть HTML-приложением для работы с анкетой, а не лендингом.

Приложение поставляется как один файл `index.html`. Пользователь открывает его напрямую в браузере или через локальный статический просмотр, но для работы первой версии не должен запускать backend.

Первый пользовательский сценарий:

1. Пользователь открывает HTML-страницу приложения в браузере.
2. Нажимает кнопку загрузки и выбирает `.docx` анкету.
3. Приложение парсит документ и показывает найденные вопросы.
4. Пользователь проверяет и правит разметку.
5. Пользователь скачивает новый размеченный `.docx`.

Рекомендуемая структура:

- левая панель: список вопросов с кодами, типами и статусами проверки;
- центральная область: исходный текст Word по блокам;
- правая панель: нормализированная карточка текущего вопроса;
- нижняя/верхняя панель действий: экспорт, сохранить, перейти к следующей ошибке.

Функции ручной разметки:

- назначить блок как начало вопроса;
- назначить блок как конец вопроса;
- объединить блоки в один вопрос;
- разделить вопрос на два;
- пометить строку как `title`;
- пометить строки как `options`;
- изменить код вопроса;
- изменить тип вопроса;
- отредактировать варианты ответов;
- отметить вопрос как проверенный.

## 13. Статусы качества

Для каждого вопроса:

- `auto_ok` - автопарсер уверен, ручная проверка не обязательна;
- `needs_review` - есть риск ошибки;
- `reviewed` - пользователь подтвердил;
- `fixed` - пользователь исправил;
- `ignored` - блок не является вопросом.

Типовые предупреждения:

- вопрос без вариантов, хотя тип похож на `Single`/`Multi`;
- варианты есть, но тип не найден;
- два вопроса с одинаковым кодом;
- код вопроса не похож на допустимый;
- таблица не разобрана на options/rows/columns;
- найден служебный маркер `СКРИН`, но не выделен `conditions`;
- слишком длинный `title`, вероятно туда попали варианты;
- между вопросами есть неразмеченные блоки.

## 14. Связь со скриптом

Хотя сравнение не входит в MVP, подготовленная структура должна совпадать с концепциями `.txt`-скрипта:

- `code`;
- `title`;
- `type`;
- `options`;
- `rows`;
- `columns`;
- `conditions`;
- `quotafilter` как отдельный будущий модуль.

На следующем этапе приложение сможет загрузить `.txt`, распарсить блоки вопросов и показать различия:

- вопрос есть в Word, но отсутствует в скрипте;
- вопрос есть в скрипте, но отсутствует в Word;
- разные формулировки;
- разные коды вариантов;
- разные тексты вариантов;
- разные типы вопросов;
- разные скрины/условия;
- квоты из паспорта не совпадают с `quotafilter`.

## 15. Нефункциональные требования

- Работать локально с файлами пользователя.
- Не требовать загрузки документов во внешние сервисы.
- Выполнять парсинг `.docx` полностью в браузере.
- Поставляться как один файл `index.html` для первой версии.
- Не требовать Python-backend или локального API-сервера в MVP.
- Поддерживать большие анкеты: текущие скрипты доходят до десятков тысяч строк, Word-файлы до нескольких мегабайт.
- Сохранять исходную трассировку: каждый элемент разметки должен ссылаться на исходный блок Word.
- Не удалять и не изменять исходные файлы.
- Все результаты сохранять рядом с проектом или в отдельной выбранной папке.

## 16. Критерии приемки MVP

MVP считается готовым, если на текущем наборе проектов:

1. Пользователь открывает HTML-страницу приложения в браузере.
2. Приложение позволяет загрузить `.docx` из любой проектной папки.
3. После загрузки показывает список автоматически найденных вопросов.
4. Для простых вопросов вроде `S1/QS1` корректно выделяет код, title и options.
5. Для вопросов с таблицами сохраняет таблицу и предлагает разметить ее как options/rows/columns.
6. Пользователь может исправить границы вопроса.
7. Пользователь может исправить title и options.
8. Пользователь может скачать новый валидный `.docx` с разметкой начала/конца вопроса, `title` и `options`.
9. В размеченном Word спорные места видимо помечены как `needs_review`.
10. Исходные `.docx`, `.txt`, `.xlsx` не изменяются.

## 17. Рекомендуемый технический подход

Backend:

- в MVP backend отсутствует;
- парсинг `.docx` выполняется в браузере;
- чтение `.docx` выполняется как ZIP/OOXML на стороне JavaScript;
- генерация нового `.docx` выполняется в браузере на основе исходного `.docx`.

Frontend:

- один файл `index.html`;
- локальное web-приложение в браузере;
- загрузка `.docx` через `<input type="file">`;
- таблица/панель вопросов;
- редактор разметки текущего вопроса;
- кнопка скачивания размеченного `.docx`;
- сохранение состояния проекта.

Хранилище:

- размеченный `.docx` рядом с проектом;
- состояние ручных правок и статусов хранится локально в браузере.

## 18. Основные риски

- В Word нет единого стандарта оформления вопросов.
- Варианты ответов часто находятся в таблицах.
- Некоторые служебные строки похожи на вопросы.
- В скрипте есть технические вопросы `QEX`, `QDataM`, `QINFO`, которых может не быть в Word в таком же виде.
- Автопарсер не должен выдавать сомнительную разметку как финальную без проверки.

Главный продуктовый вывод: приложение должно быть полуавтоматическим. Автоматическое разделение ускоряет работу, но ручная проверка границ и полей вопроса является обязательной частью процесса.

## 19. Организация рабочей папки

- В корне проекта остаются только рабочие файлы приложения и основная документация.
- Тестовые примеры, ручные наборы и наборы для проверки лежат в `примеры/`.
- Сессионные заметки, сводки и артефакты прогонов хранятся в `история/`.
- Регрессионный скрипт `compare-regression.ps1` используется как отдельный локальный инструмент; итоговый отчет после прогона хранится в `история/`.
